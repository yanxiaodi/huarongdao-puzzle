# 给初学者的关卡解法搜索算法设计

本文面向了解数组、Map 和队列等基本数据结构的读者，说明项目如何自动为华容道关卡找出一条可行解。这里的“搜索”不是让程序像人一样理解棋局，而是把棋盘表示成数据，枚举合法移动，再有方向地寻找通关局面。

## 先把棋局变成三个问题

程序只需要回答三件事：

1. **现在是什么局面？** 每个棋子的坐标。
2. **下一步能做什么？** 沿棋子允许的方向移动若干格，而且不能出界或碰到其他棋子。
3. **怎样算找到答案？** 曹操棋子到达出口位置，也就是曹操棋子左上角坐标为 `(1, 3)`。

项目棋盘是 4 列 × 5 行，坐标从 0 开始。比如棋子左上角坐标是 `(2, 1)`，表示从左数第 3 列、从上数第 2 行；棋子占几格由关卡数据给出。通关坐标 `(1, 3)` 同样是从 0 开始计数。图片、颜色、动画不参与搜索。

一次移动按“移动命令”计一步：棋子从原地滑动 1 格或多格，都只算一个命令。这和玩家拖动棋子的计步方式一致。

## 把所有可能的棋局看成一张图

可以把每种不同的棋盘局面想成图上的一个点，把一次合法移动想成连接两个点的一条线：

```text
初始局面 --合法移动--> 局面 A --合法移动--> 局面 B --...--> 通关局面
```

算法从初始局面出发，不断试走新的合法移动。走到曹操在出口的局面时，就找到了答案。这样做的好处是，棋盘只需要遵守规则；算法不需要预先写下“正确走法”。

## 搜索时保存什么

搜索中的一个“状态节点”包含这些信息：

| 字段 | 初学者可以这样理解 |
| --- | --- |
| `positions` | 棋子坐标数组；每个坐标用一个数字表示，`y * 4 + x`。 |
| `key` | 这个局面的短标识，用来查 Map，判断以前是否见过。 |
| `parent` | 这个局面是从哪个节点走来的。 |
| `move` | 从父节点走到这里时执行的那条命令。 |
| `depth` | 从初始局面走了多少条命令，也就是目前的步数。 |
| `heuristic` | 对“还要花多少步”的粗略估计。 |
| `priority` | 用来决定搜索先后顺序的分数。 |

坐标数组和节点数组保存具体数据；优先队列决定下一个展开哪个局面；`Map` 记录每种局面目前找到的最好路径。它们都是常见数据结构，只是组合起来解决了棋盘搜索问题。

## 如何枚举下一步

对当前局面，生成器会依次检查每个棋子、该棋子允许的方向，以及每个可能的移动格数。例如检查一枚竖向棋子向上移动 1 格、2 格、3 格……。每个候选命令都交给和游戏共用的移动规则：

- 合法：得到新的坐标，形成一个新状态。
- 非法：不加入搜索。若某个方向上的距离已经被棋子挡住，更远的距离也不可能通过它，因此该方向可以停止继续尝试。

新状态不保留游戏画面，只保留位置数据。这让搜索可以快速地创建和比较大量局面。

## 为什么不直接用普通队列

最直接的办法是广度优先搜索：用先进先出的队列，先检查 1 步能到的局面，再检查 2 步能到的局面。每条边都代表一条移动命令，所以广度优先搜索可以保证先找到步数最少的路径。

问题是，华容道每个局面都有许多可能移动。局面会一层层快速增加，而很多移动最终会绕回以前见过的局面。只用普通队列，可能要检查非常多的局面才接近出口。

项目改用带方向提示的搜索：优先检查“已经走的步数不多、看起来也比较接近通关”的局面。这个方法使用**优先队列**：每次取出分数最低的状态节点继续搜索，而不是单纯按进入队列的时间取出。实现使用小顶堆；加入或取出节点时只调整树的一条路径，比每次扫描整个队列找最低分更省工作。

## 分数如何给搜索指路

项目对每个状态计算三个数：

- `g`：已经走过的步数，对应代码中的 `depth`。
- `h`：还需要多少步的粗略估计，对应 `heuristic`。
- 优先分数：`g + 2 × h`，对应 `priority`。

例如，局面甲已经走 2 步，估计还差 4 步，分数为 `2 + 2×4 = 10`；局面乙已经走 5 步，估计还差 2 步，分数为 `5 + 2×2 = 9`。优先队列会先检查局面乙，因为它的分数更低。

这里的 `h` 不是保证准确的答案，只是帮助排序的提示。当前估计大致这样计算：

1. 目标棋子还没到出口的横坐标，就至少需要一次横向调整；纵坐标还没到位，就至少需要一次纵向调整。
2. 分别估算“先横向、再纵向”和“先纵向、再横向”两条直达路线中，有多少不同棋子挡住曹操。
3. 取挡子较少的路线，再加上尚未到位的方向数，作为 `h`。

这个估计能让搜索偏向出口附近、障碍较少的局面，但它看不到所有后续依赖。例如一个挡路棋子本身也可能被别的棋子挡住。因此它适合加快“找出一条解”，不能证明找到的就是最短解。系数 2 让程序更愿意跟随这个估计，换取更少的搜索工作。

## 如何避免重复搜索同一局面

一个局面可能通过不同走法再次到达。生成器会把局面编码成 `key`，并放入 `Map`：

- 以前没见过：记录它并加入优先队列。
- 以前见过，而且旧路径步数不多于新路径：跳过新路径。
- 找到了更短的到达方式：更新 Map，再加入优先队列。

这能避免算法反复从较差的路径重走同一棋盘。优先队列里偶尔会留有旧节点；取出时如果 Map 已经指向更新的节点，就跳过旧节点。

项目还利用了相同棋子的对称性。尺寸和可移动方向都相同的普通棋子，互换身份不会改变哪些局面可以到达。生成搜索键时，会把这类棋子的位置排序后再编码。比如只交换两枚相同小兵的位置，不会被当作一个全新的局面。实际棋步仍保留关卡中的棋子 ID。

## 找到终点后如何还原走法

搜索不在每个节点里复制从头开始的整条路径，只保存“父节点编号”和“刚才那一步”。找到通关节点后，沿 `parent` 一直回到初始节点，收集沿途的 `move`，最后把收集结果倒过来，就得到正向解法。

这与链表的想法类似：每个节点只指向前一个节点。这样既能还原完整路径，又避免在搜索过程中复制很多重复的路径数组。

## 为什么找到后还要再验证

搜索阶段为了加快速度，使用针对固定关卡创建的快速移动函数，减少重复检查关卡定义的开销。搜索成功后，生成器会用游戏公开的 `applyMove` 从初始棋盘重新执行每一条命令，并用 `hasWon` 检查最终局面。

只有 406 关都生成并通过验证后，程序才替换输出文件。如果任何关卡失败，错误信息会包含关卡 ID，旧文件不会被半份新数据覆盖。这样把“搜索快不快”和“发布的数据是否合法”分开处理。

## 这套设计的取舍

- 目标是给每关找一条合法通关路线，不是计算最少步数；已有的 `minSteps` 评分数据保持不变。
- 搜索在生成阶段离线运行。浏览器只加载 `public/data/solutions.json` 并播放，不会在玩家设备上搜索棋局。
- 如果未来必须保证最短步数，可以改用广度优先搜索，或重新设计满足最短路保证的启发式再使用 A*；需要接受搜索量可能显著增加。
